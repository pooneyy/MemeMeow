## Context

变更动机见 [proposal.md](proposal.md)，外部行为见本 change 的四份 delta spec。

当前新父 Job 为四个固定阶段统一写入 `queued`，只有未启用的自动重命名写入 `skipped`。Worker 每次推进前调用阶段有效性检查；如果已有产物仍有效，就不创建叶子 Task，直接把阶段标记为成功。因此父 Job 创建时记录的是候选顺序，真正执行范围在运行期间才决定。

现有父 Job 与独立阶段 Task 使用不同的活动去重身份，并允许二者同时存在。同一配置的重复父 Job 请求还会复用活动 Job。这些规则原本用于节省模型调用和支持独立阶段操作，但会让完整重试跳过用户明确要求执行的阶段，也允许两种模式竞争同一图片产物。

本设计依赖现有的图片处理 Job、pipeline/standalone Task、自动重命名第四阶段和图片级 PostgreSQL advisory transaction lock。`add-task-scoped-reverse-image-search` 对活动 Job 的策略冲突规则继续有效，但新的同图活动处理检查优先于“相同选项复用”。

## Goals / Non-Goals

**Goals:**

- 让父 Job 在创建事务中形成可恢复、可查询且不会被 Worker 改写的阶段计划。
- 让完整重试、修复未就绪和普通首次处理使用同一套阶段计划表达方式，但具有不同的计划生成规则。
- 让所有用户发起的图片重新处理请求在同一图片上严格互斥，并保持批量请求的逐图隔离。
- 继续保留目标、scope、SHA、配置、claim、外部 attempt 和结果写回校验。

**Non-Goals:**

- 不引入通用 DAG、任意阶段组合编辑器或第二套父任务系统。
- 不改变四个阶段的既有顺序、Agent grant、callback fencing、独立 Task 执行器或产物存储格式。
- 不把展示名称纳入文本语义 hash；只修复自动重命名 warning 时不自动重跑文本向量。
- 不在开源核心加入账户、订阅、计量、模型目录或服务器路径策略。

## Decisions

### 1. 父 Job 在创建时记住本次要做什么

**之前的东西是什么**

以前创建父 Job 时，视觉、Agent、自动重命名和文本向量阶段大多都先写成 `queued`。这只表示“以后按顺序看看”，没有记录“这一次到底要不要执行”。只有没有启用自动重命名时，自动重命名阶段才会直接写成 `skipped`。

**之前的东西为什么这么设计**

这样设计是为了让 Worker 在真正执行时再检查缓存。如果旧的视觉向量、Agent 结果或文本向量还有效，就可以少跑一次模型，节省时间和资源。

**之前的东西有什么问题**

父 Job 创建时看起来已经接受了用户的选择，但真正执行什么要等 Worker 再决定。于是用户选择“完整重试”时，Worker 可能把所有阶段都跳过，用户无法从父 Job 判断这次到底有没有重新执行。

**新的东西是什么**

创建父 Job 时同时写入本次处理方式和每个阶段的执行计划：

- 要执行的阶段写成 `planned=true`，状态从 `queued` 开始；
- 已经有合格结果、本次不需要执行的阶段写成 `planned=false`、`status=skipped`、原因是 `already_ready`；
- 没有启用的自动重命名写成 `planned=false`、`status=skipped`、原因是 `disabled`。

公开的阶段项固定返回 `stage`、`status`、`planned`、`skip_reason` 和可选的 `task_id`。`skipped` 只表示“本次没有执行”，不表示新 Job 已经重新完成了这个阶段。

**新的东西如何解决这个问题**

用户在创建父 Job 时看到的处理方式，就是这个 Job 后面实际执行的范围。服务重启、Worker 重试或重复检查时都读取已经保存的计划，不再重新猜测用户当时想做什么。

**新的东西的原理是什么**

把“要不要执行”从 Worker 的运行时判断，提前到父 Job 创建时决定。计划放在已有的阶段记录里，而不是另建一张计划表，这样阶段状态、阶段任务和执行计划只有一个地方保存，不会出现两份记录互相不一致。

**例子**

一张图片的视觉向量和文本向量都已经有效，用户选择“修复所有未就绪”。创建父 Job 时，这两个阶段记为 `skipped/already_ready`；如果自动重命名是 `warning`，只有自动重命名记为 `queued/planned=true`。Worker 重启多少次，都只会尝试自动重命名。

### 2. 父 Job 的三种处理方式在创建时采用不同的执行计划

**之前的东西是什么**

以前普通处理、完整重试和“处理未就绪”基本都走同一条提交路径。父 Job 创建后，Worker 再根据已有产物决定从哪一个阶段开始，用户没有办法明确区分“首次处理”“全部重跑”和“只补缺失部分”。

**之前的东西为什么这么设计**

因为多数情况下旧产物确实可以继续使用。从最早失效的阶段继续执行，能减少不必要的视觉分析、Agent 调用和文本向量计算。

**之前的东西有什么问题**

这个省资源的规则覆盖了用户意图：完整重试也会变成“从缓存能用的地方继续”。另外，只看单个阶段的状态还不够。Agent 重新执行可能改变语境，后面的文本向量也要跟着更新；自动重命名只是展示名称变化，通常不需要重跑文本向量。

**新的东西是什么**

创建父 Job 时把处理方式分成三种；独立阶段处理不创建父 Job，不属于这三种父 Job 处理方式：

- **普通处理**：缺少或已经过期的阶段列入计划，仍然有效的阶段记为本次不执行；
- **完整重试**：所有已启用阶段都列入计划，旧产物不能把计划内阶段变成跳过；
- **修复所有未就绪**：只把当前确实需要修复、以及会被它影响的后续阶段列入计划；

独立阶段处理单独使用 standalone Task，只执行用户点选的一个阶段，不创建父 Job 的其他阶段。独立 Agent Task 成功后，只让不匹配新语境的旧文本向量失效，不自动创建文本向量、自动重命名或父 Job。

修复计划按当前事实确定：

| 当前问题 | 修复阶段 |
|---|---|
| 只有视觉结果未就绪 | 视觉 |
| Agent 未就绪 | Agent、启用的自动重命名、文本向量 |
| 只有自动重命名为 `warning` | 自动重命名 |
| 只有文本向量未就绪 | 文本向量 |
| 同时有多个问题 | 上述阶段的合集，仍按固定顺序执行 |

普通处理使用同一套记录方式：阶段缺失或过期时 `planned=true`，阶段仍然有效时 `planned=false`、原因是 `already_ready`；自动重命名没有启用时原因是 `disabled`。

**新的东西如何解决这个问题**

完整重试不会再被缓存悄悄改成部分重试；修复也不会为了一个小问题把整条链全部重跑。服务端先确定范围，再创建 Job，Worker 只负责完成这个范围。

**新的东西的原理是什么**

阶段是否需要执行，取决于阶段之间真实的数据关系，而不是简单地看到哪一行失败就只跑哪一行。视觉结果是 Agent 执行时需要的前置条件，但重新生成一个仍对应当前图片的视觉向量，不会自动让已有 Agent 语境和文本向量失效。Agent 会改变语义内容，所以 Agent 修复必须带上文本向量；自动重命名当前只改展示名称，不改变文本语义内容，所以单独修复自动重命名不带文本向量。独立 Agent Task 是单独的一次用户操作，不能因为它成功就接回某个旧父 Job。

**例子**

新图片第一次进入普通处理时，如果没有任何结果，四个已启用阶段都列入计划；如果只有自动重命名是 `warning`，点击“修复所有未就绪”只创建自动重命名 Task。如果 Agent 语境失败，视觉结果仍有效，则创建 Agent、自动重命名和文本向量三个阶段，但不重新创建视觉 Task。用户点击“完整重试”时，则不管旧结果是否有效，所有已启用阶段都重新执行。用户单独重试 Agent 时，只创建 standalone Agent Task；它成功后旧文本向量失效，但不会自动创建文本 Task。

### 3. Worker 只能执行父 Job 已经确定的计划

**之前的东西是什么**

以前 Worker 走到某个阶段时，会调用阶段有效性检查。如果发现对应产物还有效，就直接把这个阶段标成成功，不创建新的叶子 Task。

**之前的东西为什么这么设计**

阶段有效性检查原本是为了处理服务重启、重复提交和图片库补齐，让系统能够安全复用没有变化的结果。

**之前的东西有什么问题**

这个检查同时承担了两件事：一是判断旧结果能不能作为安全输入，二是决定用户这次是否真的要重跑。两件事混在一起，就会让完整重试失去意义，也会让同一个 Job 在不同时间得到不同执行范围。

**新的东西是什么**

Worker 只选择父 Job 中 `planned=true` 且还没有收束的第一个阶段。计划内阶段必须创建并执行本次 Job 自己的叶子 Task，即使旧产物仍然有效。叶子 Task 仍然只使用现有的 `queued -> running -> succeeded|failed` 状态；只有自动重命名的叶子 Task 失败时，父阶段才可以按可降级规则收束为 `warning`。

运行时检查仍然保留，但只检查能不能安全执行和写回：scope、Meme、图片 SHA、文件身份、阶段输入、配置、当前 `claim generation` 和 attempt 是否仍然匹配。所有进度、终态和图片结果写回都必须验证当前 `claim generation`；旧租约的 Worker 不能写回。Agent 继续使用全局、scope 和资源池的并发上限以及持久的公平调度，队列里等待的数量不能变成新的拒绝条件。运行时检查不能把计划内阶段改成跳过。

**新的东西如何解决这个问题**

用户选择的完整重试一定会创建新的阶段 Task；修复 Job 也只会执行创建时列入的最小范围。服务重启后继续读取同一份计划，不会因为缓存状态变化而扩大或缩小任务。

**新的东西的原理是什么**

把“是否执行”与“是否允许执行”分开：创建 Job 时决定前者，Worker 运行时验证后者。若计划中跳过的旧结果后来被删除或失效，Job 使用稳定错误 `image_processing_plan_stale` 停止，不能临时把被跳过的阶段加入计划，更不能在缺少结果时假装成功。计划内已经有 `queued` 或 `running` 叶子 Task 时，恢复同一个 Task，不创建第二个逻辑 Task。

**例子**

完整重试 Job 运行到视觉阶段时，即使旧视觉向量还有效，也必须创建新的视觉 Task；只有这个新 Task 成功，视觉阶段才算完成。相反，一个修复 Job 创建时认为视觉结果有效，执行到后面发现视觉结果被删除，就以 `image_processing_plan_stale` 停止，而不是偷偷补跑视觉。

### 4. 所有用户发起的同图处理请求必须互相排斥

**之前的东西是什么**

以前完整 Job 和独立阶段 Task 使用各自的去重规则。同样选项的完整 Job 可以复用已有活动 Job，而独立阶段 Task 又有自己的活动记录；两种方式没有统一检查同一张图片是否已经在处理。

**之前的东西为什么这么设计**

这样可以让重复点击尽量复用已有任务，也能让完整处理和独立阶段处理各自工作，不必改动原来的任务服务。

**之前的东西有什么问题**

同一张图片可能同时存在父 Job 和独立阶段 Task，两个任务都可能写同一份结果。只在 HTTP 层先查再创建还会有并发漏洞：两个请求都可能查到“当前没有活动任务”，随后各自创建成功。

**新的东西是什么**

完整重试、修复和独立阶段处理统一经过同一个图片处理提交过程，并在同一个短事务中完成：

1. 锁定当前 scope、Meme 和图片 SHA；
2. 查询同图的 `queued`/`running` 父 Job；
3. 查询同图的 `queued`/`running` pipeline 或 standalone 阶段 Task；
4. 只要找到一个活动处理，就返回 `image_processing_active`；
5. 没有活动处理时，在同一事务中创建新的父 Job 或独立 Task。

Job repository 和 Task repository 使用这个提交过程持有的同一个 Session。图片阶段 Task 保存结构化的目标 Meme 和图片 SHA，并建立活动查询索引；不能只从 JSON payload 临时猜目标。

父 Job 内部为自己创建叶子 Task 不经过这项“用户新请求”检查，因为它已经有父 Job 和阶段关系证明归属。文件读取、额度授权、调度和模型调用都在事务提交后进行。

对于这三种用户重新处理请求，图片活动检查优先于处理选项比较：只要已经有 `queued` 或 `running` 的同图处理，就返回 `image_processing_active`，即使新请求选择了不同的处理策略。`generation_policy_conflict` 只保留给不属于这三种用户重新处理请求的既有内部策略冲突，不能覆盖图片活动检查。

**新的东西如何解决这个问题**

同一张图片只要已经排队或正在运行，任何新的完整重试、修复或独立阶段请求都会明确失败，不会复用、覆盖或并行创建任务。终态历史不会阻止新的请求。批量请求只拒绝发生冲突的图片，不影响其他图片。

**新的东西的原理是什么**

数据库锁把“检查有没有活动任务”和“创建新任务”变成一个不可插入第二个请求的动作。两个并发请求会排队进入同一把图片锁，第一个创建成功后，第二个一定读到活动记录。跨模式查询使用同一个图片目标事实，所以父 Job 和独立 Task 不能互相绕过。

**例子**

图片 A 已有排队中的独立 Agent Task，此时用户点击完整重试，返回 `image_processing_active`，不创建父 Job。图片 B 没有活动任务，和图片 A 一起出现在批量修复中时，A 被逐图拒绝，B 仍然创建修复 Job。两个请求同时重试图片 C 时，只有一个能创建 Job，另一个收到冲突。

### 5. 批量操作逐图处理，并返回看得懂的结果

**之前的东西是什么**

选中图片的入口使用 `include_unready=true` 表达重试；scope 级入口枚举未就绪图片并返回 `submitted_count`、`reused_count`、`conflict_count` 等汇总。活动任务在相同选项下可能被当成复用结果返回，scope 级入口也没有把“只修复哪个阶段”作为父 Job 创建时的固定计划展示出来。

**之前的东西为什么这么设计**

复用活动任务可以减少重复提交，批量接口只返回汇总可以让响应保持简单，也能让一次请求尽快结束，不等待真正的模型处理。

**之前的东西有什么问题**

用户看不出“完整重试”和“修复所有未就绪”的区别，也看不出某一张图片到底是已经提交、正在处理、无需修复，还是提交失败。如果一张图片冲突，前端还可能把整批误显示成失败，或者把旧任务误显示成这次已经提交。

**新的东西是什么**

选中图片入口继续表示“完整重试”；scope 级 `/images/processing/unready` 的产品名称改为“修复所有未就绪”。两个入口都逐图处理，不把整批放进一个大事务：

- `submitted`：本次创建了新的父 Job；
- `processing_active`：这张图片已有活动处理，原因是 `image_processing_active`；
- `not_needed`：复核后已经没有需要修复的阶段，原因是 `already_ready`；
- `failed`：这张图片提交失败，并返回有限的稳定原因。

每项返回 `meme_id`、`category`、可选 `reason` 和可选 `processing_job_id`。`submitted` 必须返回本次新建的 `processing_job_id`；`processing_active`、`not_needed` 和 `failed` 不返回 Job 或 Task 标识，活动冲突不返回旧 Job 或 Task 标识。选中图片入口返回 `batch_id/results`；scope 级修复另外返回目标数和各分类数量。为了兼容旧客户端，`reused_count` 暂时保留但固定为零。

**新的东西如何解决这个问题**

用户可以直接看到每张图片的处理结果。批量中一张图片正在处理，只会影响这一张；其他图片照常创建任务。前端可以分别显示“已提交”“正在处理”“无需修复”和“提交失败”，而不会把异步执行结果冒充成已经完成。

**新的东西的原理是什么**

批量操作只负责提交任务，不等待任务完成。第一次枚举时已经没有候选图片时直接返回 `target_count=0`；只有已经枚举为候选、但在图片级锁内复核后变为就绪的图片才返回 `not_needed/already_ready`。每张图片使用自己的短事务和自己的父 Job 计划，逐图结果由提交事实生成，汇总数字再由逐图结果计算。这样单张图片的锁冲突、目标变化或数据库错误不会回滚已经成功提交的其他图片。

**例子**

一次“修复所有未就绪”扫描到 A、B、C：A 已有活动 Job，B 的 Agent 未就绪，C 在枚举时仍是候选但锁内已经就绪。响应中 A 是 `processing_active/image_processing_active`，B 是 `submitted` 并带新的 Job ID，C 是 `not_needed/already_ready`；`submitted_count=1`、`conflict_count=1`、`not_needed_count=1`。如果 C 在第一次枚举时就已就绪，则不会出现在结果中。A 的冲突不会撤销 B 的修复。

### 6. 开源核心和服务器适配分阶段交付

父 Job 计划、Worker 推进、图片级活动门禁、公共 HTTP 结果和前端文案属于开源公共核心，必须先在 MemeMeow 实施、测试并形成边界清晰的 commit。服务器版本在用户审核并完成上游同步后通过普通 merge 引入该精确 commit，再处理模型选择、账户授权、计量、grant 资源和路径校验等适配。

OpenSpec 与实现不得在 Server 中平行复制公共算法。Server 的批量入口可以在公共逐图结果上增加用户控制信息，但不能改变完整重试、修复计划或图片级排他的含义。

## Risks / Trade-offs

- [完整重试会增加模型调用和额度消耗] → 确认界面明确说明全部已启用阶段会重新执行；服务器适配层在创建父 Job 前完成授权和额度检查。
- [创建计划后产物状态可能变化] → 用户意图优先，计划保持不变；运行时只做安全校验，目标或输入变化时明确失败，不静默重算。
- [跨父 Job 与独立 Task 查询增加提交事务工作量] → 为图片阶段 Task 增加结构化目标列和活动索引，只查询单 scope、单 Meme、单 SHA，并保持事务中不读取文件、不申请 grant、不调用模型。
- [部署时已有活动 Job 仍按旧规则推进] → 切换前停止新的图片处理提交并排空活动 Job；无法排空时保留旧 Job 的普通处理方式，新规则只用于迁移后创建的 Job。
- [扩展 `skipped` 含义可能让旧前端误解] → 阶段项固定返回 `planned` 和 `skip_reason`；历史没有原因的自动重命名 `skipped` 只读解释为 `disabled`。
- [活动请求从复用改为冲突会影响旧调用方] → 在变更说明和 API 文档中标记行为破坏；批量响应提供稳定逐图原因，兼容窗口可保留零值汇总字段。

## Migration Plan

1. 迁移前检查所有图片阶段 Task 的目标字段、Job 关系和活动状态；无法可靠绑定图片的活动历史 Task 必须自然进入终态或由受控运维流程收束为 `failed`，否则以 `image_processing_history_unresolved` 阻止启用新提交入口。
2. 执行只向前 migration：为父 Job 增加非空受约束处理方式；为阶段关系增加非空计划标识和条件性不执行原因；为图片 Task 增加结构化目标 Meme、图片 SHA、约束和活动查询索引；显式重建受影响的 CHECK。
3. 历史 Job 回填为普通处理；历史自动重命名 `skipped` 回填为未计划且原因为 `disabled`；其他历史阶段保持既有执行事实。能由可信 Job 关系或受校验 payload 证明的图片 Task 回填目标列，终态且无法证明的历史项保持只读兼容。
4. 部署写入和读取新计划但尚未开放新入口的兼容代码，确认旧 Job 快照、任务历史和阶段进度仍可读；新记录必须满足 `planned=false` 时 reason 非空、`planned=true` 时 reason 为空的约束。
5. 切换父 Job 创建、完整重试、修复枚举和独立阶段提交到共享 Session 的图片级门禁，再切换 Worker 为严格执行持久计划。
6. 更新公共 HTTP 类型、API 文档和前端文案，启用逐图结果分类，并移除活动执行复用的界面表达。
7. 在单图并发、父 Job 与 standalone Task 跨模式冲突、服务重启、目标变化、自动重命名 warning 和批量部分成功场景下完成回归后，再形成开源 commit 供审核。

数据库 migration 不提供破坏性 downgrade。应用回滚时先停止新提交并等待新计划 Job 收束，再回退到仍能只读理解新增字段的兼容版本；旧应用无法理解通用阶段 `skipped` 时不得直接恢复旧 Worker。数据库保留新增字段和计划事实，历史 Job、Task 和产物不得删除或改写。
