## Context

本 change 的原因和范围见 `proposal.md`。这里重点说明具体怎样实现。

现在，`opencode run --format json` 会在运行时逐行输出 JSON 事件。Executor 已经把这些内容写进临时 stdout 文件，但只在进程结束后读取文件并取得 session 标识。任务页面则另外查询 OpenCode SQLite 中的 `session` 和 `part` 表，用 `step-start` 和 `step-finish` 计算轮次。

OpenCode 生产镜像固定使用 `1.18.18`。该版本支持从配置目录加载 JavaScript 或 TypeScript 插件，也提供 `experimental.chat.system.transform`，允许插件在模型请求发出前补充系统提示。但是，插件拿不到一个可靠的主任务轮次编号，也没有可靠的强制停止接口。

后端已经会在等待任务结束时反复查询 Executor 状态，也已经有防止旧 Worker 覆盖新 Worker 结果的 claim generation 检查。因此，新功能应复用这些现成路径，不再建立第二条状态通道。

## Goals / Non-Goals

**Goals:**

- 同一次 OpenCode 运行只计算一份轮次结果，供强制停止、后端保存和页面展示共同使用。
- 每个模型可以有不同的正常轮次、提醒轮次和宽限轮次，并且任务开始后不受后来配置变化影响。
- 插件加载和计数异常必须清楚报错；单次提醒允许提前、延后或漏发，硬停止不能依赖提醒是否准确。
- 恢复同一任务时继续使用已经消耗的轮次，不能重新获得完整额度。
- 保留旧任务的页面展示能力，同时让新任务不再依赖查询 OpenCode SQLite 才能取得轮次。

**Non-Goals:**

- 不修改 OpenCode 核心。
- 不使用 OpenCode 的 `agent.steps` 作为最终强制上限，因为它不能可靠阻止后续工具执行。
- 不把轮次当成工具调用次数、token 数量、费用或任务完成百分比。
- 不让插件负责进程终止、计费、权限、任务主状态或数据库写入。
- 不在本 change 中增加服务器版本专属的账户、订阅和额度功能。

## Decisions

### 1. 从 OpenCode JSON 输出统一识别轮次

#### 之前的东西是什么

Executor 让 `opencode run --format json` 把逐行 JSON 写进临时 stdout 文件。运行期间，Executor 只检查进程是否结束、用户是否取消以及是否超时；进程结束后才读取文件取得 session 标识。页面需要显示 Agent 活跃度时，再查询 OpenCode SQLite 的 `session` 和 `part` 表，按 `step-start` 和 `step-finish` 计算轮次。

#### 之前为什么这么设计

临时文件能完整保留命令输出，方便在任务结束后查错，也避免父进程没有及时读取管道时把子进程堵住。页面只需要展示大致活跃情况，所以当时直接复用 OpenCode 已经写入 SQLite 的会话记录，改动较小。

#### 之前的东西有什么问题

Executor 并不知道当前执行到第几轮，因此无法按轮次停止进程。页面和未来的限制功能如果各自计算，会出现一个显示 8 轮、另一个已经按 9 轮处理的情况。OpenCode 还可能重复输出同一个 `part` 的更新；如果只按行数累计，同一轮会被重复计算。

#### 新的东西是什么

在公共 executor 包中增加一个只负责读取轮次事件的模块。它不连接数据库，不访问网络，也不控制进程。它接收 stdout 的新增字节，拼成完整 JSON 行，只识别外层 `step_start`、`step_finish`，并同时核对内层 `part.type` 是否分别为 `step-start`、`step-finish`。

统一结果包含：已经结束的轮数 `completed_turns`、已经开始的轮数 `consumed_turns`、当前是否有一轮尚未结束 `turn_running`，以及最后活动时间 `last_activity_at`。这里的“一轮”是一次模型步骤，同一轮里的多个工具调用不另算轮次。

#### 新的东西如何解决这个问题

Executor、后端和页面不再各算一遍。轮次模块先把原始事件变成唯一结果，Executor 用它判断是否停止，再把同一结果交给后端保存和页面展示。重复事件会在进入计数前被丢弃，因此不会增加额度消耗。

#### 新的东西的原理是什么

模块保留一段“还没有换行”的字节，下一次读取时继续拼接，避免半行 JSON 被误判为损坏。每个合法事件用 `(sessionID, part.id, part.type)` 去重：同一 `part.id` 的开始事件只算一次，结束事件也只算一次，但开始和结束彼此不是重复事件。

第一个合法事件会把本次任务绑定到一个 session。后续如果出现另一个 session，立即返回明确的绑定错误。单行过大、JSON 层级过深、编码错误或字段不符合约定时，也返回稳定的轮次跟踪错误，不能悄悄改成不限轮次。事件自带可信时间时使用事件时间，否则使用 Executor 收到事件时的 UTC 时间。

#### 例子

输入依次为：`part.id=p1` 的 `step_start`、同一个 `p1` 的重复 `step_start`、工具调用事件、`p1` 的 `step_finish`、`part.id=p2` 的 `step_start`。处理时，重复的 `p1 step_start` 被去掉，工具调用不计轮次。结果是 `completed_turns=1`、`consumed_turns=2`、`turn_running=true`；强制停止和页面展示都读取这三个值。

### 2. Executor 实时读取输出并负责强制停止

#### 之前的东西是什么

Executor 现在负责启动 OpenCode、检查取消和总超时，并通过 `ProcessSupervisor` 终止和回收进程组。它虽然保存 stdout 文件，但运行期间不读取新增内容，也没有轮次上限。

#### 之前为什么这么设计

原来的执行边界只有“任务完成、用户取消、运行超时”几种情况。轮次只用于页面观察，所以进程控制不需要理解 OpenCode 的步骤事件。

#### 之前的东西有什么问题

模型接近免费额度时，Executor 无法知道它已经运行多少轮。仅靠给模型发文字提醒不能阻止它继续调用工具；仅靠总超时又无法表达“这个模型最多允许 15 轮”这样的规则。

#### 新的东西是什么

`TaskState` 保存本次任务固定下来的轮次策略和当前轮次结果。OpenCode 启动后，Executor 在原有进程检查循环中增量读取 stdout 文件，并把新事件交给统一轮次模块。达到允许的最后一轮以后，如果又出现下一轮的 `step_start`，Executor 使用现有进程组终止流程强制结束任务。

#### 新的东西如何解决这个问题

强制停止发生在真正管理 OpenCode 进程的 Executor 中，不依赖模型是否听从提醒，也不依赖后端和页面是否及时取得最新状态。为了保持实现简单，Executor 不尝试在第 16 次请求发出前预测 OpenCode 是否还会继续，而是在观察到第 16 个 `step_start` 后马上终止。原来的取消、超时、SIGTERM、有限等待和 SIGKILL 流程可以直接复用。

#### 新的东西的原理是什么

策略中的正常上限和宽限轮数相加，得到允许工作的最大轮数。例如正常上限 10、宽限 5，表示第 1 至第 15 轮可以正常工作。当收到第 16 个唯一 `step_start` 时，第 16 次模型请求可能已经发出并产生费用；Executor 接受这个代价，立即终止该任务的 OpenCode 进程组，并返回稳定错误 `agent_turn_limit_exceeded`。系统不承诺在第 16 次请求发出前拦截。

如果进程已经无法确认是否被回收，任务继续使用现有的 `unknown_execution` 状态，不能假装已经安全停止。Executor 的状态接口只返回轮次数、是否正在运行、最近活动时间和提醒状态，不返回原始提示词、工具参数、推理内容或完整事件。

#### 例子

输入策略是 `normal=10`、`reminder=9`、`grace=5`。第 1 至第 8 轮正常执行，插件尽量在第 9 轮请求中加入收尾提醒，第 9 至第 15 轮仍允许模型完成验证或修复。OpenCode 发出第 16 次模型请求并输出第 16 个 `step_start` 后，轮次模块得到 `consumed_turns=16`，Executor 马上终止当前任务的进程组。第 16 次请求可能产生费用，但不能继续完成这一轮；任务结果为 `agent_turn_limit_exceeded`，其他任务不受影响。

### 3. 复用 Executor 状态轮询，把同一份轮次交给后端和页面

#### 之前的东西是什么

后端的 `AgentExecutorClient._wait_for_terminal` 已经会反复查询 Executor，直到任务成功或失败。页面所需的 Agent 轮次没有经过这条路径，而是在每次查询任务状态时临时读取 OpenCode SQLite。

#### 之前为什么这么设计

状态轮询最初只关心任务是否结束，SQLite 则已经保存 OpenCode 会话部件。两者各自完成单一需求，当时不需要额外保存运行中的轮次。

#### 之前的东西有什么问题

页面查询和 Executor 实际运行状态存在时间差，而且列表中的多个任务可能造成多次 SQLite 查询。更重要的是，页面读出的值并不是 Executor 用来停止任务的值，用户看到的轮次与实际限制可能不一致。

#### 新的东西是什么

扩展已有 Executor 状态响应，让它带上有限的轮次结果。`AgentExecutorClient` 在现有轮询中校验这份结果，并在数值发生变化时调用内部活动回调。`OpenCodeRunner` 把回调交给任务服务，任务服务再把结果写入 PostgreSQL。页面仍通过原有任务接口读取数据，不直接访问 Executor。

#### 新的东西如何解决这个问题

不增加 Executor 主动回调 API，也不增加页面到 Executor 的连接。原有轮询同时搬运任务终态和轮次结果，页面读取后端已经保存的同一份数据。这样，强制停止、持久化和展示都从同一个源头出发。

#### 新的东西的原理是什么

Task 保存页面当前需要的轮次结果，Agent attempt 保存本次执行固定下来的策略、累计消耗和最后结果。写入时沿用 claim generation 检查：只有当前 Worker 的 claim 可以更新，旧 Worker 的迟到数据会被拒绝。

活动回调保存失败时，后端记录明确且有限的错误，并保留最后一次可信结果；它不能改变 Executor 已经做出的强制停止判断。任务写入最终成功或失败状态前，再保存一次最终轮次结果。公开接口继续使用现有的 `agent_completed_turns`、`agent_turn_running` 和 `agent_last_activity_at` 字段。

#### 例子

Executor 状态返回 `completed_turns=8`、`consumed_turns=9`、`turn_running=true`。后端轮询发现这份结果和上次不同，于是通过当前 claim 写入 PostgreSQL。用户随后打开任务页面，接口返回 `agent_completed_turns=8`、`agent_turn_running=true`。此时页面显示的“已完成 8 轮，第 9 轮进行中”和 Executor 用于限制的状态一致。

### 4. 按模型配置策略，并在任务开始时固定下来

#### 之前的东西是什么

现有模型目录描述可以使用哪些模型和变体，但没有正常轮次、提醒轮次和宽限轮次。任务开始后也没有一份独立保存的轮次策略。

#### 之前为什么这么设计

原来的任务只受总超时和运行环境限制，不需要按模型区分轮次。模型目录只负责选择模型，因此没有保存执行额度的必要。

#### 之前的东西有什么问题

免费模型和付费模型的允许轮数不同，使用一个全局数值不能表达这种差异。如果任务运行中读取最新配置，管理员修改目录后，已经执行到一半的任务可能突然增加或减少额度，恢复任务时也无法确定应沿用哪一版规则。

#### 新的东西是什么

在公共模型目录中为每个可执行 Agent 任务的模型增加轮次策略，至少包含正常轮次上限 `normal`、发送提醒的轮次 `reminder` 和额外允许的轮数 `grace`。任务创建时由受信任的服务端按实际模型和变体选中策略，并把完整副本保存到 Task 和 attempt。

#### 新的东西如何解决这个问题

不同模型可以使用不同上限。任务一旦创建，就一直使用当时保存的数值；模型目录后来变化只影响新任务。客户端不能自行提交更大的轮数，Executor 只接受服务端已经校验且与模型相符的策略。

#### 新的东西的原理是什么

公共校验函数要求 `normal` 和 `reminder` 为正整数、`grace` 为非负整数，并要求 `reminder <= normal`。允许完成的最大轮数只由 `normal + grace` 计算，调用方不再额外传一个可能互相矛盾的数值。配置缺失或关系不合法时，任务创建立即失败，不以无限轮次继续。OpenCode 的 `agent.steps` 即使保留较大兼容值，也不作为判断依据。

#### 例子

模型目录中，免费模型 A 配置 `normal=10`、`reminder=9`、`grace=5`，付费模型 B 配置 `normal=40`、`reminder=35`、`grace=8`。用户用模型 A 创建任务后，Task 保存 10、9、5。管理员随后把模型 A 的正常上限改成 12，这个旧任务仍在第 9 轮提醒、最多允许 15 轮；之后创建的新任务才使用新配置。

### 5. OpenCode 插件只负责发送一次收尾提醒

#### 之前的东西是什么

当前 OpenCode 运行没有专门的轮次提醒插件。OpenCode 自带的 `agent.steps` 在接近数值时可以补充收尾文字，但在当前 CLI 路径中不能可靠阻止模型继续执行工具，也不能替代 Executor 的进程控制。

#### 之前为什么这么设计

以前没有按模型轮次限制，依靠任务提示词、总超时和模型自行结束已经能够完成运行。也没有必要在镜像中维护额外插件。

#### 之前的东西有什么问题

模型不知道自己即将用完允许轮次，可能在最后几轮继续扩展工作，而不是整理结果。反过来，如果把插件当成强制限制，模型忽略提示、插件计数不准或插件异常时就会失去保护。

#### 新的东西是什么

镜像预装一个本地 JavaScript 插件，使用 OpenCode 等待执行完成的 `experimental.chat.system.transform` 接口，尽量在模型进入提醒轮次时追加固定的中文系统提示，要求它优先完成必要工作、验证已有结果并生成报告。每个 attempt 最多追加一次。这里的“尽量”表示允许提前、延后或漏发，不承诺精确命中某一轮。

#### 新的东西如何解决这个问题

当插件能够判断主任务进度时，模型会在硬停止之前收到收尾信号，并仍有几轮时间修复错误。提醒放在系统提示中，不会伪造一条新的用户要求，也不会因为提醒本身多算一轮。插件判断不准、漏发提醒或模型不配合时，Executor 仍按统一轮次结果停止进程。

#### 新的东西的原理是什么

插件从任务配置读取提醒轮次、目标模型和策略版本，并结合主 session 中可以确认的历史，估计当前是否接近提醒轮次。它尽量过滤标题生成、上下文压缩和子任务等非主任务请求，但现有插件接口没有可靠的主任务轮次编号，所以无法保证判断准确。无法确认时可以不提醒，硬限制仍由 Executor 独立执行。

插件文件和依赖放在镜像内普通 Agent 用户不可写的只读位置，任务生成的 OpenCode 配置使用绝对文件 URL 加载。启动前检查文件存在、可读、版本与 OpenCode `1.18.18` 相符，并确认目标接口已经注册。找不到插件、加载失败、初始化失败或版本不兼容时，在第一次模型调用前返回稳定错误，避免任务在没有可用提醒能力的情况下开始。插件成功启动后，如果某一次提醒判断或提示注入发生运行时异常，只记录明确的提醒错误并允许任务继续，不假装提醒成功；Executor 仍独立执行硬限制。

#### 例子

某 attempt 的策略是第 9 轮提醒。插件从主 session 历史判断已经有 8 个模型步骤完成，而且当前请求使用任务固定下来的模型，于是在系统提示末尾增加“请尽快完成必要工作、验证结果并生成报告”，并记录本 attempt 已提醒。相同请求重试时不再追加第二遍。如果一次上下文压缩让插件误以为还没到第 9 轮，它可以延后提醒或漏发；Executor 仍会在收到第 16 个 `step_start` 后终止进程。

### 6. 恢复同一任务时继续使用累计轮次

#### 之前的东西是什么

现有任务可以在 Worker 或执行进程中断后恢复同一个 OpenCode session，但系统没有持久保存用于限制的累计轮次和策略。每次新启动的 Executor 状态都从当前进程开始。

#### 之前为什么这么设计

以前没有轮次预算，恢复只需要找回 session 和任务状态。重新启动进程不会影响总超时之外的额度，因此不需要携带累计数。

#### 之前的东西有什么问题

如果每次恢复都从零计数，一个最多允许 15 轮的任务可以通过重启反复取得 15 轮。旧 Worker 还可能在新 Worker 接管以后迟到写回，把较新的轮次结果覆盖掉。

#### 新的东西是什么

后端持久保存任务策略和已经消耗的轮数。恢复同一 session 时，把原策略、累计消耗、session 标识和 attempt 标识一起交给 Executor。Executor 校验它们属于同一任务后，从累计值继续计算。

#### 新的东西如何解决这个问题

进程、Worker 或服务重启不再重置额度。当前 claim 才能保存新轮次和终态，旧 attempt 的迟到事件不会覆盖新 attempt。已经因为轮次超限而停止的任务，也不能自动伪装成一个全新 session 再获得额度。

#### 新的东西的原理是什么

累计消耗保存在 Task 和 attempt 的受约束字段中。恢复开始前，Executor 检查 session、attempt、模型和策略副本是否一致；不一致就明确报错。新的 stdout 事件在原累计值上增加，后端写回时继续使用 claim generation 检查。轮次超限不按模型供应商的短暂故障无限重试，是否允许用户显式恢复仍由现有重试规则决定。

#### 例子

任务使用 `normal=10`、`reminder=9`、`grace=5`，在第 8 轮结束后 Worker 重启。PostgreSQL 中保存 `consumed_turns=8` 和原策略。新 attempt 恢复同一 session 后，第一个新的 `step_start` 被算作第 9 轮并触发提醒阶段，而不是第 1 轮；继续运行到第 16 个累计 `step_start` 时仍会被强制终止。

### 7. 新任务使用持久轮次，SQLite 只兼容历史任务

#### 之前的东西是什么

任务页面通过 `OpenCodeActivityReader` 查询 OpenCode SQLite，找到 session 和 `part` 记录后计算已完成轮数、当前是否运行和最近活动时间。OpenCode 自己也使用这份 SQLite 保存 session，以便恢复会话。

#### 之前为什么这么设计

SQLite 已经包含页面所需的活动记录，原功能只做只读展示，不需要修改 Executor 和 PostgreSQL。对于已经存在的任务，这也是目前唯一可取得轮次的来源。

#### 之前的东西有什么问题

SQLite 可能繁忙、不可读或随 OpenCode 版本改变表结构。页面列出多个任务时还会重复查询。它的写入时机不受 Executor 控制，因此不适合做实时强制限制，也无法保证与 Executor 判断完全一致。

#### 新的东西是什么

新创建的任务只使用 Executor 产生并保存到 PostgreSQL 的轮次结果作为页面主要来源。`OpenCodeActivityReader` 暂时保留，只在迁移前的历史任务没有 Executor 轮次结果时进行只读补充。OpenCode SQLite 本身继续用于 session 保存和恢复，本 change 不删除它。

#### 新的东西如何解决这个问题

新任务的页面展示不再受 SQLite 锁、读取权限或表结构变化影响，且直接显示 Executor 用于限制的同一份结果。历史任务仍能尽量显示原有活动信息，不需要一次性回填无法可靠计算的数据。

#### 新的东西的原理是什么

任务接口先检查 PostgreSQL 是否有 Executor 轮次结果：有就直接返回；只有没有结果且确认是历史任务时，才执行有限的 SQLite 兼容读取。SQLite 不存在、被锁定、结构不兼容或找不到 session 时，接口仍返回正常任务状态，只省略无法确认的活动字段，不能虚构为 0 轮。兼容读取永远不参与硬停止。

#### 例子

任务甲是新任务，PostgreSQL 已保存 `completed_turns=8`，即使 OpenCode SQLite 此时被锁定，页面仍显示已完成 8 轮。任务乙是迁移前的历史任务，没有持久轮次，接口才查询 SQLite；如果读到 12 个完整步骤，就显示 12 轮，如果数据库不可读，就返回任务乙的名称和状态但省略 Agent 活动字段。两种情况下，SQLite 都不会决定是否终止进程。

## Risks / Trade-offs

- [OpenCode 写入 stdout 文件与 Executor 读到新内容之间会有短暂延迟，第 16 次模型请求可能已经发出并产生费用] → 接受最多多发出一次请求，以换取简单可靠的外层实现；收到 `step_start` 后立即进入进程组回收，不等待 SQLite。
- [一个模型轮次可以包含多个工具调用，轮数不能代表真实费用或副作用数量] → 接口和页面只把它叫作模型步骤，不显示完成百分比；费用、工具权限和超时继续由原有规则处理。
- [插件没有公开且可靠的主任务轮次编号，标题生成或上下文压缩可能让提醒提前、延后或漏发] → 明确接受提醒尽力准确；插件按主 session、模型和可确认历史过滤，Executor 的 JSON 事件计数是唯一强制依据。
- [后端保存轮次失败时，页面可能暂时显示旧数值] → 保留最后一次可信结果并记录错误；Executor 继续独立执行限制，任务进入终态前再保存一次。
- [Executor 或 API 重启可能丢失尚未保存的最后一个事件] → 运行期间按现有短轮询保存，终态前再次保存；恢复时沿用已持久的累计数，无法确认时明确报错而不是重置。
- [OpenCode 升级可能改变 JSON 事件格式或插件接口] → 生产版本继续固定为 `1.18.18`；升级前必须通过事件格式、插件加载和实际运行测试。
- [任务可写配置如果能够替换插件，会影响后续任务] → 插件源码和依赖放在镜像只读路径，运行时测试覆盖 Bash、Python 和 Node 的修改尝试。

## Migration Plan

1. 在开源仓库增加模型轮次策略、JSON 事件读取和统一轮次结果；默认不改变历史任务的 SQLite 兼容读取。
2. 增加 PostgreSQL migration，让 Task 和 Agent attempt 保存策略、累计轮次及当前或最终轮次结果；历史记录允许为空。
3. 在 Agent 镜像的只读位置预装提醒插件，并在任务启动前检查 OpenCode 版本、插件接口和文件权限。
4. 让 Executor 在运行期间读取 stdout、执行强制停止并通过现有状态接口返回轮次；让后端现有轮询保存轮次。
5. 只对新任务启用按模型策略和实时结果，确认页面展示、提醒、宽限停止、插件失败和恢复行为；历史任务继续按需读取 SQLite。
6. 完成单元测试、进程测试、PostgreSQL 测试、Docker 实际任务和前端回归后，在开源仓库形成边界清晰的 commit，交给用户审核。通过审核并按用户要求进入官方开源远端后，服务器版本才能合并该精确 commit，再增加账户、订阅和计量适配。

回滚时，先停止创建带新策略的任务，等待正在运行的新任务按已保存的策略结束。旧程序必须能忽略新增字段并继续读取历史任务。不能立即删除数据库字段，也不能直接换回不认识累计轮次的旧 Worker；应等所有使用新策略的任务进入终态后，再用后续 migration 清理。
